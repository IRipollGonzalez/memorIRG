# CLAUDE.md — MemorIRG

## What this project is

A local-first flashcard app: drop a CSV into `data/`, and every column that isn't `category`/`subcategory` becomes a possible card side — no fixed schema. Python 3.12 + FastAPI backend, React/TypeScript frontend, CSV files as the only data store — no database, no cloud accounts. Ships three ways from one codebase: a dev server, a native macOS `.app` (FastAPI + pywebview), and a fully static build on GitHub Pages (no backend — see "Web app" below) for phones/other devices.

## How to run

```bash
# Backend (dev)
source .venv/bin/activate
uvicorn backend.main:app --reload --port 8000

# Frontend (dev, separate terminal)
npm --prefix frontend run dev
```

Tests:

```bash
pytest
npm --prefix frontend run test
```

## Architecture

```text
backend/domain/          ← pure layer: models (FlashcardRecord, Topic, StudySession), exceptions, validators
backend/repositories/    ← data access: topics_repository (reads/cleans CSVs), session_store (in-memory dict)
backend/services/        ← business logic: topic_service, deck_service, session_service
backend/api/             ← thin HTTP routes (topics, sessions), delegate to services
backend/main.py          ← orchestrator: mounts routers + built frontend, maps domain exceptions to HTTP errors
backend/config.py        ← single source of truth for MEMORIRG_* env vars
frontend/src/pages/      ← one component per screen (just StudyPage — this app has one screen)
frontend/src/api/        ← topics.ts, sessions.ts — branch on IS_STATIC between HTTP calls and lib/local/*
frontend/src/lib/local/  ← client-side mirror of domain/repositories/services, for the static build only
```

```text
frontend → api client (HTTP) → backend/api
backend/api → services → repositories → domain
backend/main.py → everything
```

## Key design decisions

**CSV as the only data store** — No database, no ORM, no migrations. Every `*.csv` in `data/` is a topic; every non-metadata column is a possible card side. This is the app's whole reason for existing over a generic flashcard app, and it's cheap enough (a handful of small hand-edited files) that a database would add ceremony without benefit. `topics_repository.py` caches parsed topics by `(path, mtime)` so repeated requests in a session don't re-parse an unchanged file.

**Sessions live in server-side memory, not a database** — `session_store.py` is a plain in-memory dict keyed by a UUID, populated by `session_service.create_session()`. This matches the original app's behavior: closing MemorIRG loses the current session's shuffle/position by design. It works because this is a single-user local app — the backend process's lifetime already matches "one user, one session."

**Immutable session state** — `session_service` never mutates a `StudySession`. Every transition (`flip_card`, `go_next`, `go_previous`) returns a new instance via `dataclasses.replace()`. State transitions are explicit and unit-testable without touching HTTP at all.

**Shuffle once, never re-shuffle mid-session** — the deck order is fixed at `create_session()` time, so "Previous" always retraces the same order rather than a live-reshuffled one.

**One uvicorn process serving both API and frontend in packaged mode** — no subprocess, no mode-dispatch env var (unlike the retired Streamlit version, which needed two OS processes because Streamlit's own event loop couldn't share a thread with pywebview). `backend/main.py` branches on whether `frontend/dist/` exists rather than an env flag, so dev and packaged mode share the identical codebase.

**Side selection swap-on-conflict is a pure frontend function** — `frontend/src/lib/topicFilters.ts`'s `resolveOtherSide()` auto-swaps the other side when a user picks the same content column for both, mirroring the original app's dropdown behavior. The backend still validates `side_1 != side_2` at the API boundary (`InvalidSideSelectionError` → 400) as a defensive check, but the interactive swap itself is UI, not business logic.

**Recent sessions live in localStorage, not the backend** — `frontend/src/lib/recentSessions.ts` keeps the last 6 studied deck configs (topic, category/subcategory, sides) per browser, shown as a resume dock on the empty/landing state. This is deliberately client-only and per-device: it needs no session-store schema on the backend, and matches the "closing the app loses session state" design decision already in place for the active study session — recents are a UI convenience layered on top, not persisted app state.

**Media card sides (image/YouTube/audio) are a column-naming convention, not a schema change** — a content label ending in `_image`/`_youtube`/`_audio` (`frontend/src/lib/media.ts`) renders as that media type instead of text; a cell value is either a bare filename (resolved against `frontend/public/media/`, which Vite copies into every build — dev, desktop, and static) or a full `http(s)://` URL, auto-detected. Nothing in `backend/domain` changed to support this — `FlashcardRecord.values` was always `dict[str, str]`, so a filename or URL is just another string value; the rendering decision lives entirely in the frontend. Because the repo is public, treat `public/media/` as published content — prefer linking out (e.g. a YouTube URL) over checking in copyrighted recordings/images you don't hold the rights to.

**Static build has no backend — `frontend/src/lib/local/` is a hand-ported mirror of `backend/{repositories,services}`** — GitHub Pages only serves static files, so `IS_STATIC` (`frontend/src/lib/env.ts`, set via `VITE_DATA_SOURCE=static` in `.env.static`) switches `frontend/src/api/*.ts` from HTTP calls to these local, in-browser equivalents: `topicsEngine.ts` reads the bundled `src/data/topics.json` instead of the filesystem, `deckEngine.ts`/`sessionEngine.ts` reimplement filtering/shuffling/session-transitions in TypeScript (same immutable-replace pattern as `session_service.py`, an in-memory `Map` instead of `session_store.py`'s dict). The desktop/dev app is untouched — it still always talks to the real backend. Keep the two in sync by hand if session/filter *behavior* ever changes; `topics.json`'s *content* never needs manual sync, since `scripts/build_topics_json.py` regenerates it from the same CSVs via the real `topics_repository` parser.

## Desktop app (native macOS)

One process, two threads — no subprocess, no mode-dispatch env var:

```text
MemorIRG.app  [double-click in Finder]
  └── One process, two threads
        ├── Main thread:       pywebview loading window → webview.start()  (blocks here)
        └── Background thread: allocate free port → uvicorn.Server(...).run()
              serving backend.main:app (API routes + built frontend/dist/ as static files)
              → poll 127.0.0.1:<port> until it accepts connections
              → window.load_url(...) once ready
```

| Mode | User data | Logs |
|---|---|---|
| Dev | `<project_root>/data/` | `~/Library/Application Support/MemorIRG/logs/` |
| Packaged | `~/Library/Application Support/MemorIRG/data/` | same |

First launch copies the bundled default CSVs into App Support if that `data/` dir is empty (`desktop/data_init.py`); every later launch is a no-op on existing files — never overwrites a user's own decks. Application Support is shared by `APP_NAME` alone, not by which source folder produced the build — never `rm -rf` anything under `~/Library/Application Support/MemorIRG/` without inspecting it first.

## Desktop build

```bash
# one-time per machine
./desktop/create_build_venv.sh

# every build
source .venv-desktop/bin/activate
./build_desktop.sh
# → dist/MemorIRG.app
```

`build_desktop.sh` builds the frontend, cleans `build/`+`dist/`, runs PyInstaller against `desktop/MemorIRG.spec`, then ad-hoc codesigns to strip iCloud Drive extended attributes (this project lives under iCloud Drive; synced xattrs otherwise break the signature). Requires Python ≥3.11, Node.js, and `assets/icon.icns`.

## Web app (GitHub Pages)

Live at **https://iripollgonzalez.github.io/memorIRG/** — a fully static build with no backend (see the "Static build has no backend" design decision above). `.github/workflows/deploy-pages.yml` rebuilds and republishes automatically on every push to `main` that touches `data/`, `frontend/`, `backend/`, or the script:

```text
push to main
  → pip install -e .                        (backend needed only to parse CSVs)
  → python scripts/build_topics_json.py      (data/*.csv -> frontend/src/data/topics.json)
  → npm ci --prefix frontend
  → npm run build:static --prefix frontend   (vite build --mode static, base=/memorIRG/)
  → actions/upload-pages-artifact + actions/deploy-pages
```

To build/preview the static variant locally:

```bash
source .venv/bin/activate
python scripts/build_topics_json.py
npm --prefix frontend run build:static
npm --prefix frontend run preview -- --base=/memorIRG/
```

`vite.config.ts`'s `base` and `main.tsx`'s `BrowserRouter basename` both key off Vite's `mode`/`BASE_URL` — `/` in dev and packaged mode, `/memorIRG/` only in `--mode static` (GitHub Pages project-site hosting, not domain root).

## Adding a new topic

**Dev / desktop app**: drop a `*.csv` file into `data/` (dev) or into `~/Library/Application Support/MemorIRG/data/` (packaged app) and reload the page — no code change, no restart. `topics_repository`'s mtime-based cache picks up new/changed files automatically.

**Web app (GitHub Pages)**: there's no server to reload — drop the CSV into `data/`, commit, and push to `main`. The Actions workflow above regenerates `topics.json` and redeploys automatically (usually live within a minute or two of the push).

Both paths share the same rule: reserved column names are `category`, `subcategory` (case-insensitive); every other column becomes a content label the user can pick as Side 1 or Side 2; a topic needs at least 2 non-metadata columns.

### Image / YouTube / audio card sides

Name a column with one of these suffixes and its cell values render as media instead of text — the Side 1/Side 2 dropdowns just show it like any other column:

| Column suffix | Renders as | Cell value |
|---|---|---|
| `*_image` (or exactly `image`) | `<img>` | filename in `frontend/public/media/`, or a full `http(s)://` URL |
| `*_youtube` | embedded YouTube player | a video ID, a full `youtube.com/watch?v=...` or `youtu.be/...` URL |
| `*_audio` | `<audio controls>` | filename in `frontend/public/media/`, or a full `http(s)://` URL |

Example `data/art.csv`:

```csv
category,artist,artwork_image
Impressionism,Claude Monet,water-lilies.jpg
```

If `artwork_image`'s value isn't a URL, drop the actual file at `frontend/public/media/water-lilies.jpg` — commit it alongside the CSV for the desktop app and dev mode, and push both for the web app (same `git add`/`commit`/`push` as any other topic change; the Actions workflow doesn't need to know about media, since `npm run build:static` copies `public/` verbatim). **The repo is public** — prefer a YouTube link over checking in an audio file for actual recordings you don't hold the rights to; for images, public-domain art (most work from before ~1928) is fine to host directly, anything more recent is safer linked out too.
